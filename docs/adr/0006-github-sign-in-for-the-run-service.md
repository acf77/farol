# The run service signs users in with GitHub and issues its own sessions

ADR 0005 rejected OAuth because the service had one owner. It now serves the desktop app and other apps for several people, so a shared API key per client no longer says who started a run. We decided that people sign in with GitHub (a GitHub App, or an OAuth App) and the service issues its own session token; API keys stay for scripts and CI. The flow is: sign in, keep remote pipelines in the committed `.farol/pipelines.json`, start a run from the desktop (snapshot upload) or another app (API request), and get back a JSON result. The pipeline never changes the project; the calling app decides separately whether to change anything, locally or remotely.

The service does the GitHub exchange itself — device flow for the desktop and CLI, authorization code with PKCE for web and mobile against an allowlist of redirect URIs — so the client secret never leaves it, reads `/user`, and drops the GitHub token. Users are keyed by GitHub's numeric id. A session is `fs1.<payload>.<hmac>` with a 7-day expiry and no server-side session store; revocation is per user (`sessionsValidAfter`, `disabledAt`) in a 0600 JSON file re-read per request, like API keys. Nobody may sign in until an allowlist of logins or organizations is set, or `FAROL_ALLOW_ANY_GITHUB_USER=1`: signing in proves identity, it does not make running code on the service safe. Runs and workspaces belong to `key:<id>` or `user:<github id>`. Anonymous mode (`FAROL_ALLOW_ANONYMOUS`) is removed; a service started with it refuses to start.

Signing in does not make running code safe, so the sandbox is the boundary. Nothing written in a sandbox persists or leaves it: each run gets a fresh sandbox, destroyed afterwards, with no credentials, and only output, exit codes and the JSON result come back. Railway sandboxes no longer capture a shared dependency checkpoint from the first run, which let one run plant files in every later run; they boot only from a checkpoint the operator built (`RAILWAY_CHECKPOINT`). The workspace endpoint the desktop uses is no longer a remote shell: it pins the pipelines from its own snapshot and runs only their shell steps, with `${name}` slots filled by single-quoted values. Every sandbox has a hard lifetime (`FAROL_MAX_RUN_MINUTES`), and each user or key gets a share of the pool (`FAROL_MAX_RUNS_PER_OWNER`). We did not filter commands by content: with `bash -lc` any blocklist is bypassed trivially.

Results stay JSON over HTTP, gzip-compressible, with a versioned schema. Run time is spent booting sandboxes and running steps, not parsing a few KB of mostly log text.

Considered and rejected: passing GitHub tokens through as the API credential (every request would hit GitHub, and a token minted for another app would be accepted); storing GitHub tokens (not needed until the service fetches repositories itself); a session database with refresh tokens (more state than a single-process alpha needs); protobuf or gRPC for results (no measurable gain here, and it costs codegen, browser support and `curl`-ability — Connect-RPC is the path if a schema-first multi-language contract is wanted later).
