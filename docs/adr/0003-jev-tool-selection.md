# Jev selects a tool focus before each managed Chat turn

Managed Chat used to launch every coding CLI with its full default tool set. Jev already scored post-turn pipeline selection and step verdicts; it did not sit on the tool path. Narrowing tools per turn is the higher-leverage use of an evaluation model: less wandering, fewer irrelevant tools, and clearer policy — but only if uncertain scores never strand a coding turn.

We decided that before each Build-mode agent invocation Farol asks Jev one **Choice** among host-prepared foci (`inspect`, `implement`, `verify`, `answer`). Inspection tools always stay available. Each focus maps to optional capability families (`edit`, `shell`, `web`); the host re-checks the returned id and candidates fingerprint before applying argv or a prompt clause. A focus applies only when the winning probability clears `JEV_TOOL_CONFIDENCE`; mid-band answers, unknown ids, fingerprint drift, timeouts, and missing keys fail open to the full tool set. Claude and OMP receive a native `--tools` allowlist; Codex, Cursor, OpenCode, and OpenRouter keep their argv unchanged and receive the same capability policy as a mandatory prompt clause (including read-only shell inspection when that is how the provider reads files). Plan mode keeps its existing review gates and never asks Jev for tools. Pipeline auto-selection remains a separate, permanent post-turn responsibility. Prompt-policy violations observed in tool cards are logged for diagnosis only in v1 — Farol does not kill the process mid-tool.

We rejected advisory-only injection (no real narrowing), shadow-then-enforce as the initial rollout (the product decision was immediate enforcement), failing closed when a provider lacks a per-run allowlist, removing pipeline auto-selection while building tool selection, auto-killing runs on the first omitted-family tool card, and one independent boolean per optional family (absolute Nouls do not compete the way a relative focus Choice does).
