# Chat context: resume the CLI's own session, rebuild from the chat when it cannot

Every managed Chat turn is a fresh CLI process. Farol used to rebuild the whole context into one prompt each turn: the task plus the user's follow-ups, cut from the front at 100k characters (so a long chat lost the original task first) and never including the agent's own replies. We decided that when the next turn runs on the same CLI in the same directory, Farol resumes that CLI's saved session (`claude --resume`, `codex exec resume`, `cursor-agent --resume`, `opencode run --session`) and sends only the new request, because the CLI already holds every reply and tool result and compacts its own context. When it cannot resume — a fallback or a provider switch, a restart without a session, OMP, or a CLI that refuses the session — Farol sends a **Rebuilt history**: the task (capped), the newest follow-ups that fit a 100k-character budget (oldest dropped first, with a note that they were), and the agent's **Handoff note**. The agent maintains that note with a hidden `FAROL_HANDOFF:` control line, so the summary costs no extra model call and is written by the one agent that knows the work. The chat pane saves only the session reference and the note; after a restart the task and follow-ups are rebuilt from the transcript's user messages.

Considered and rejected: a larger character cap (it only delays losing the task, and pays for resending the whole history every turn); a Farol summarizer call when the budget is exceeded (an extra model call, latency and failure mode on the turn path, and it would summarize without seeing the replies); saving the full history on the pane (the workspace file is rewritten often); a shared context service across checkouts or users (transcripts leak secrets and go stale across branches — durable knowledge belongs in committed files such as `CONTEXT.md` and ADRs).
