# Farol calls the GitHub API itself, as the user it signed in

Farol read and changed pull requests through the `gh` CLI, which the user had to install and log in to separately although Farol already signs them in with GitHub (ADR 0006). The Git actions agents ask for (ADR 0001) would have inherited that.

We decided that the service hands the GitHub token a sign-in produced back to a client that asks for it (`githubAccess: true`), with the session, and keeps none itself. A client that does not ask gets what it always got: a session, no GitHub token, and no `repo` scope on its sign-in. The desktop app, which asks, stores the token encrypted next to the session, refreshes one that expires through the service (`POST /v1/auth/github/refresh`, because only the service holds GitHub's client secret, and the refreshed token must belong to the caller), and calls the REST and GraphQL API directly for pull requests, their checks and which of them branch protection requires, and merges. The same token signs `git push`, `fetch` and `pull` in to github.com through a Farol credential helper git runs when the transport needs a password, after client-side hooks, so a hook does not inherit the token in `GIT_CONFIG_VALUE_*`; it is never on a command line. When GitHub refuses it (git exits 128 with a login error), the command runs once more with the credentials the machine already has, with its hooks on: git checks the login when it first contacts the remote, before `pre-push` runs, and a push that got further must still pass the pipelines bound to it. A hook that blocks a push exits 1 and is never retried.

The `gh` CLI and the machine's own git credentials are the fallback, used when the API cannot be asked: no sign-in, a remote that is not github.com, or no network. A GitHub error such as a refused merge is GitHub's answer and is reported as it is, not retried through the CLI. When there is no token and `gh` cannot stand in, the Git panel offers Sign in with GitHub.

We rejected having the service make the GitHub calls for the desktop (every call and all the state would live on a shared service), keeping the token on the service, a second GitHub sign-in inside the desktop app, and replacing local git with a library (status, commit and diff are local work the API cannot do).

Consequences: the device flow asks GitHub for the `repo` scope only when the client asked for GitHub access, and for `read:org` whenever access is limited to organizations; a GitHub App needs the matching permissions instead. The browser flow returns the grant on the same terms. People who signed in before this change have a session but no GitHub token, and sign in once more. A refresh, a refusal or a 401 that arrives after sign-out or a new sign-in is dropped: every answer is checked against the grant stored now before it saves or deletes anything, so a late answer can neither bring back the credentials of an account that signed out nor overwrite or delete a newer sign-in. Pull requests are looked up in the `upstream` remote when there is one, else `origin`, so a fork's pull requests are found. Git passes its environment to the hooks it runs, so a repository's own `pre-push` hook can read the token during a push; those hooks already run with the user's rights, but it is one more reason to keep the scopes as narrow as GitHub allows.
