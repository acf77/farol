# Agent Git actions run inside Farol, gated by pipelines

Agents already work in a Git checkout, and Farol already runs pipelines for them. We want the agent to commit a turn's changes — and optionally push or open a pull request — with the same visibility and hookability as a pipeline, rather than running git in its own shell.

We decided that managed Chat requests a **Git action** with a `FAROL_GIT:` control line (agents outside managed Chat use the `git_status` / `git_commit` / `git_push` / `git_create_pr` MCP tools), the action executes inside the running app through the existing bridge, and when `.farol` binds a **Git hook pipeline** to that action Farol runs it as a gate first: on pass the action runs, on fail it does not and the failure returns to the agent. A machine-scoped Settings **Git actions toggle**, on by default with no per-project override, can refuse every agent Git action.

We rejected letting the agent run `git` itself (nothing gates it and the app cannot show it), adding provider-approval MCP tool calls to managed Chat (approval varies by provider, and the managed harness owns execution), and reusing the user's **Commit selection** for the agent's commit (that selection is the Source Control page's, not the turn's changes).

Consequences: Farol owns git execution, so a **Git action** shows on the existing **Git panel** and the **Git log**, and the pipeline gate applies before it. An **Agent commit** contains only the files the turn changed. Plan mode ignores `FAROL_GIT` because it is read-only. The toggle is per machine, so a user cannot disable agent commits for one repository without disabling them everywhere.

How it works: Farol commits and pushes through the same functions as the Git panel, so the gate is the managed hook Farol already installs for pipelines bound to `commit` or `push`; git runs it before the action completes, and the output of a hook that blocks the action returns to the agent like a failed validation. Farol performs an action after the turn's validation pipelines pass, from the top of the repository (an agent may work in a subfolder, and git names changed files from the top). Stop ends the queue: the action in flight finishes, since a commit or push is not safe to tear down halfway, but none queued behind it runs, and neither does one still waiting for its turn on the checkout. The actions of a turn hold to the branch the checkout was on when the first began (or to no branch, when HEAD was detached); each checks it when its turn comes, so a branch switch queued between a commit and a push stops the push, and the pull request, instead of moving them to the other branch. A managed Chat's `FAROL_GIT` commit holds the files the turn changed, found by comparing the working tree at the start and end of each attempt; the `git_commit` tool, which has no turn, requires the paths. The commit is checked against the snapshot taken when the last attempt ended, the working copy validation saw: a file that changed since is refused, and nothing stays staged. A snapshot cannot tell whose edits are whose, so when another chat ran in the same checkout during the turn Farol makes no agent commit (a worktree for each chat avoids that); the developer's own edits while a turn runs still count as the turn's. A pull request goes through the GitHub API (ADR 0008). A request over the bridge is confined by where its folder really is, symlinks resolved, to the open project and its linked worktrees; the action runs in that resolved folder, and only on a repository that belongs to that checkout, so a link inside a project that leads to another repository is refused. A managed Chat's folder comes from the renderer, so the app confines it the same way against every project it has open and their linked worktrees, and ignores the checkout the chat claims: a folder in none of them is refused, whatever repository the renderer names. Commit, push, pull, the conflict merge and the branch switch on one checkout run one at a time, for the Git panel and for agents alike, because each is several git commands, or changes what several read, and two requests could interleave: one commit staging another's files, a commit landing on a branch that was switched under it, or a push publishing that other branch. An agent's pull request takes its turn in the same line, so Stop and a branch switch reach it the way they reach a commit or a push.
